# 项目文档体系重构方案

> 目标：按成熟软件项目的文档组织方式，重新明确各文档职责边界，减少重复维护，让玩家、开发者与 AI 都能快速理解项目。
> 原则：**README 是入口，而不是所有信息的容器；每份文档只有一个清晰职责；权威信息只有一个来源；摘要可以重复，规则不要重复维护。**

---

## 一、当前文档问题

| 问题 | 说明 |
|---|---|
| README 过度膨胀 | 记录了阶段 0~12 的完整实现细节（约 300 行历史日志），已从「项目首页」变成「完整百科」 |
| AGENTS 承载历史日志 | §6「当前阶段状态」包含大量历史实现说明、测试数量、遗留事项，属于项目历史而非开发规范 |
| 重复维护 | 阶段实现说明在 README、AGENTS 两处重复出现 |
| 缺少分工 | 没有独立的「安装运行」「玩家说明」「系统架构」「代码目录」「开发状态」文档 |
| 内容过期 | AGENTS/README 记载「成就 24」，实际配置为 33 |

---

## 二、重复内容来源

- 阶段 0~12 的「完成内容」在 `README.md`「开发进度」与 `AGENTS.md`§6「当前阶段状态」中重复维护。
- 「技术栈」在 README、AGENTS、BACKEND_STANDARDS、技术方案中重复出现（摘要层重复可接受，权威仍以技术方案为准）。
- 「内容规模」在 README 与需求文档中重复（README 应给出实际当前规模而非目标规模）。

## 四、README 当前问题

1. 「开发进度」把阶段 0~12 的完整实现细节全部写在 README，违背「README 是入口而非百科」。
2. 「内容规模」表给出的是**目标规模**（如技能约 80~100、道具约 40~60），未区分「当前实际规模」。
3. 缺少对 `docs/` 下辅助文档（QUICK_START / GAMEPLAY / ARCHITECTURE / PROJECT_STRUCTURE / DEVELOPMENT_STATUS）的索引。

---

## 五、AGENTS 当前问题

- §6「当前阶段状态」累计了 13 个阶段的实现说明、遗留说明、测试数量、迁移版本，属于历史日志。
- 保留的强约束（权威文档清单、架构边界、固定业务规则、禁止事项、开发流程）应继续保留，但历史实现记录应迁移至 `DEVELOPMENT_STATUS`。

- README 与需求文档：玩法不冲突。

- ARCHITECTURE 与技术方案：不改变架构边界。
- PROJECT_STRUCTURE 与实际代码：目录真实存在。
- DEVELOPMENT_STATUS 与开发规划 / AGENTS / 代码：状态一致。
