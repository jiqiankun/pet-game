# 宠物精灵游戏第一阶段技术方案说明

**版本：V1.0**  
**适用阶段：第一阶段**  
**部署方式：Spring Boot Executable JAR + MySQL**  
**项目定位：个人开发、个人部署、个人游玩的轻量 Web 宠物精灵游戏**

---

# 1. 文档目的

本文档用于说明宠物精灵游戏第一阶段的技术实现方案，作为后续项目初始化、模块划分、数据库设计、接口设计、战斗系统开发和部署的技术依据。

技术方案遵循以下原则：

1. 优先使用成熟、熟悉的 Java + Vue 技术体系；
2. 不为了“游戏”引入过重的游戏开发框架；
3. 开发阶段前后端分离，发布阶段合并为单 JAR；
4. 游戏核心数值配置化；
5. 游戏内容配置和玩家存档数据严格分离；
6. 战斗规则统一由后端 BattleEngine 计算；
7. 手动战斗和自动战斗复用同一套战斗引擎；
8. 第一阶段不引入 Redis、MQ、微服务、WebSocket 等非必要组件；
9. 保证未来增加进化、突破、新宠物、新地图时可以继续扩展；
10. 保持项目整体结构简单，适合单人长期维护。

# 2. 总体技术方案

推荐技术栈：

| 层级 | 技术 |
|---|---|
| 前端框架 | Vue 3 |
| 开发语言 | TypeScript |
| 构建工具 | Vite |
| 状态管理 | Pinia |
| 路由 | Vue Router |
| 2D游戏渲染 | Phaser |
| 2D地图编辑 | Tiled |
| 后端 | Java 21 + Spring Boot 3.5.x |
| ORM | MyBatis-Plus |
| 数据库 | MySQL 8.4 LTS |
| 数据迁移 | Flyway |
| API | REST JSON |
| 构建工具 | Maven |
| 部署 | Executable JAR |
| Web服务器 | Spring Boot内置Web服务器 |
| 容器 | 不使用Docker |
| Nginx | 第一阶段不需要 |

Vue 官方当前仍推荐基于 Vite 的 Vue 3 工具链；Phaser 官方提供 Vite / TypeScript 等项目模板，因此 Vue + Phaser 的组合适合当前浏览器端2D方案。

Spring Boot 官方支持通过 `java -jar` 运行可执行 JAR，3.5 系列仍处于官方稳定版本线；因此本项目选择 Java 21 + Spring Boot 3.5.x 作为相对保守的技术基线，而不为了追求最新大版本直接升级 Spring Boot 4.x。

数据库采用 MySQL 8.4 LTS。MySQL 官方将 8.4 定义为 LTS 系列，适合希望保持稳定功能集合和较长支持周期的环境。

# 21. 战斗持久化策略

战斗进行中：

> 不持久化完整BattleContext。

战斗结束时统一写入：

- 宠物HP
- 掉落
- 金币
- 经验池
- 图鉴
- Boss幸运值
- Boss次数
- 统计
- 捕获宠物

这样可以减少大量无意义数据库交互。

如果服务在战斗过程中异常关闭：

> 当前未完成战斗直接丢弃。

由于战斗失败本身没有资源惩罚，所以第一阶段完全可以接受。

# 25. 技能模型

技能配置不要写大量：

```java
if (skillId.equals("xxx"))
```

采用配置驱动。

例如：

```yaml
id: FIRE_BLAZE_CLAW
name: 烈焰爪

element: FIRE
source: INNATE
skillType: ACTIVE
damageType: PHYSICAL
target: ENEMY_SINGLE

baseValue: 50

scaling:
  strength: 1.25

cooldown: 1
accuracy: 0.95

effects:
  - type: BURN
    chance: 0.20
    duration: 2
```

技能至少具备两个独立维度（原有单一 `category` 字段不再同时承担两个概念）：

```text
source（来源）：INNATE / BOOK / 后续预留 EVOLUTION / SPECIAL
skillType（类型）：ACTIVE / PASSIVE
```

不要使用一个字段同时承担“来源”和“主动/被动”两个概念。

系数也支持取两个属性中较高者：

```yaml
scaling:
  maxOf: [strength, spirit]
  coefficient: 1.0
```

# 30. 配置启动校验

应用启动时必须检查：

- ID重复
- 技能引用不存在
- 宠物技能不存在
- Boss掉落不存在
- 地图刷新组不存在
- 非法概率
- 非法倍率
- 非法等级
- 宠物属性不存在

发现严重错误：

> 应用启动失败。

不要等到玩家打Boss时才发现配置错误。

# 36. 技能关系

技能数据模型统一采用「SkillDefinition 与宠物技能关系分离」的设计。

## SkillDefinition（技能定义）

负责定义技能本身，与具体宠物无关：

```text
skillId
name
element
source（INNATE / BOOK / 预留 EVOLUTION / SPECIAL）
skillType（ACTIVE / PASSIVE）
damageType
target
effects
cooldown
accuracy
scaling
tags
其他战斗配置
```

## PetSpeciesSkillRelation / PetSkillUnlock（宠物技能关系）

负责描述某个宠物种族掌握哪些技能、在什么等级解锁：

```text
speciesId
skillId
unlockLevel
技能来源（INNATE 等）
是否特色技能
是否专属技能
```

同一个 skillId 允许关联多个 PetSpecies（技能共享）。BattleEngine 只关心 skillId 与 SkillDefinition，不判断技能属于共享还是专属；共享/专属属于内容层概念。

禁止出现 `if (speciesId == XXX)` 来决定技能基础行为；宠物专属技能需要的特殊机制仍优先通过 Effect 组合实现。

## 禁止复制技能定义

不得为了不同宠物复制相同技能配置（如 烬牙兽_FIRE_CLAW 与 赤曜兽_FIRE_CLAW）；效果相同的技能应统一为一个 skillId，由多个宠物引用。修改一次 SkillDefinition，所有引用宠物同时生效。

## 升级技能解锁

Pet Growth 模块支持按等级区间解锁：

```text
oldLevel → newLevel
查询 oldLevel < unlockLevel <= newLevel 范围内的全部宠物自身技能
```

一次提升多个等级时，必须一次解锁所有跨越等级节点的技能（例如 Lv.4 → Lv.21 需正确获得 Lv.5/Lv.10/Lv.15/Lv.20 技能）。

## 自身技能持久化原则

如果宠物自身技能可以由 speciesId + 当前 level 可靠推导，优先不把每个等级解锁的自身技能重复保存到 player_pet_skill，而是动态根据 PetSpeciesConfig + level 计算当前已掌握的自身技能。

player_pet_skill 主要保存：

- 当前装备的自身主动技能ID；
- 技能书学习的主动技能；
- 技能书被动；
- 特殊来源技能；
- 未来无法由等级直接推导的技能。

避免重复保存可以由静态配置稳定推导的数据。

## 技能配置校验

启动校验需覆盖：skillId 引用必须存在对应 SkillDefinition；同一宠物内 (speciesId, skillId) 关系不得重复；unlockLevel 必须在合法等级范围（1～50）；技能书学习限制配置合法。严重错误启动失败。

## 技能装配规则

> 自身主动技能最多装备4个；技能书主动技能最多学习10个、战斗中最多携带2个；**被动技能分固有被动与技能书被动两类管理**。

当前携带技能：

> 可以同时记录槽位与来源分组（自身主动槽 / 技能书主动槽 / 技能书被动启用槽）。

升级获得新自身主动技能时：槽位不足4个可自动装备到空位；已满4/4则只进入自身技能库、不自动覆盖原技能。被动解锁后自动生效，无需额外配置。

## 被动技能加载（阶段 14 重构：固有被动 + 技能书被动分离）

被动技能明确分为两大来源：

- **固有被动**（species.passives，来源 INNATE/LEVEL_UP/EVOLUTION）：宠物进入 BattleContext 时按 `unlockLevel <= level` 全部加入 `unit.passives`，**自动生效，不占槽位**。
- **技能书被动**（player_pet_skill，sourceType=SKILL_BOOK）：**已学习 ≠ 当前生效**。仅加载启用槽位（7~8，最多 2 个）中的被动；已学习未启用的不参与战斗。

装配后进行**效果组归一化/去重**（`PassiveEffectResolver`）：
- 同名被动只保留一个；
- 同 effectGroup 按 stackRule 处理：UNIQUE/HIGHEST_ONLY 取最高一个，ADDITIVE/LIMITED 允许叠加；
- 防止固有「迅捷」+ 技能书「迅捷」双倍生效。

`PassiveSkillConfig` 新增字段：`sourceType`（INNATE/LEVEL_UP/EVOLUTION/SKILL_BOOK）、`effectGroup`、`stackRule`（UNIQUE/HIGHEST_ONLY/ADDITIVE/LIMITED）、`maxStack`、`priority`。启动校验覆盖这些字段的合法值。

# 75. 技能体系补充：来源、类型与携带限制

技能配置与玩家技能数据模型正式区分两个独立维度：

```text
source（技能来源）：INNATE / BOOK / 后续预留 EVOLUTION / SPECIAL
skillType（技能类型）：ACTIVE / PASSIVE
```

携带与学习限制：

| 类别 | 规则 |
|---|---|
| 自身主动技能 | 每种族默认6个（范围5～7个），战斗中最多装备4个 |
| 自身被动技能 | 每种族默认约3个（内容建议2～5个），无池上限、无携带上限，自动生效 |
| 技能书主动技能 | 最多永久学习10个，战斗中最多携带2个，战斗中不可更换 |
| 技能书遗忘 | 达10个后学习新技能需遗忘一个；重新学习需再次消耗技能书 |
| 被动技能 | 无池上限、无携带上限，掌握后进入战斗自动生效 |

技能书主动技能与自身主动技能使用独立槽位分组，互不占用；被动不计入任何主动技能上限。

配置层预留：

```text
maxUsesPerBattle
```

用于限制少数特殊技能每场战斗的成功使用次数，第一阶段默认不启用。

| 类别 | 示例 |
|---|---|
| 持续状态 | 灼烧、中毒、混乱、隐匿、狂暴、再生 |

# 79. 技能体系补充：BattleEngine结算边界

以下关键机制的结算边界作为BattleEngine的正式约束：

## 吸血

- 按本次实际HP损失计算，不按理论伤害；
- 护盾吸收部分、过量伤害部分不计入；
- 恢复不超过最大HP，溢出丢弃，不转护盾；
- DOT、反击、反射伤害、普通被动伤害默认不吸血；
- 受禁疗与治疗效果降低影响。

## 留生一击（LeaveAtOneHpEffect）

- 致死伤害时将可捕捉目标HP保留为1，暴击也不能绕过；
- 仅在实际触发1HP保护时清除持续伤害状态（灼烧/中毒等），其他状态不清除；
- 仅对可捕捉野生宠物附加震慑，Boss不附加；
- 震慑不提高捕获率，CaptureCalculator不新增修正项。

## HP百分比交换（HpPercentageExchangeEffect）

- 不是Damage也不是Heal：不触发暴击、吸血、反击，不受防御/抗性/护盾影响，不参与属性克制，不触发“受到伤害时”被动，不计入总伤害统计；
- 交换的是HP百分比，护盾保持原值，Buff/Debuff/状态不交换；
- Boss采用交换幅度上限而非免疫：`bossHpExchangeLimit = 0.20`（单次最多改变Boss 20个百分点HP比例），具体计算方式配置化，精英预留独立限制参数。

## 其他边界

- 行动顺序干预只操作当前回合顺序，不修改基础速度永久值；
- 换宠类技能消耗本回合行动，后续换宠不额外消耗行动；
- 延迟效果需可被防御/换宠/净化/护盾应对。

# 83. 敌方胜利互动系统技术设计

## 83.1 模块定位与职责

本系统是**战败表现增强模块**（需求 §152），只负责在玩家战败后，根据获胜方类型与当前战况标签，从配置中选择一条互动并返回前端播放。**不参与战斗数值计算、不改变战败结算、不引入新在线服务。**

模块职责：

```text
玩家战败
↓
生成轻量 BattleDefeatContext
↓
识别获胜方类型（TRAINER / WILD_PET / BOSS）
↓
匹配战况标签（contexts）
↓
筛选 VictoryInteraction（专属 → 公共池）
↓
排除最近播放（防重复）
↓
按 weight 随机选择
↓
返回前端播放（文本 + 可选动作/叫声/表情）
```

## 83.2 数据配置（新增 victory-interactions.yml）

沿用既有配置体系（`GameConfigLoader` / `GameConfigRegistry` / `GameConfigValidator`），新增一个配置模型，字段使用 camelCase 与 Java 模型对齐。

```yaml
configVersion: 1
interactions:
  - id: VI_NPC_CLOSE_001
    winnerType: TRAINER      # TRAINER / WILD_PET / BOSS
    style: SARCASTIC          # 训练师 victoryStyle 或 野外 victoryBehavior
    contexts: [CLOSE_LOSS]    # 战况标签列表（空 = 通用）
    presentationType: DIALOGUE # DIALOGUE / ACTION_NARRATION / CRY
    actionId: null            # 可选动作 ID（如 YAWN / PROWL）
    cry: null                 # 可选叫声文本
    weight: 100               # 权重（越大越常见）
    rarity: COMMON            # COMMON / EASTER_EGG（彩蛋低概率）
    text: 就差一下呢，是不是更难受了？
```

对应 Java 模型（示意）：

```java
@Data
public class VictoryInteractionConfig {
    private List<Interaction> interactions = new ArrayList<>();
    @Data
    public static class Interaction {
        private String id;
        private String winnerType;    // TRAINER / WILD_PET / BOSS
        private String style;
        private List<String> contexts; // 空表示适用所有
        private String presentationType; // DIALOGUE / ACTION_NARRATION / CRY
        private String actionId;
        private String cry;
        private int weight = 100;
        private String rarity = "COMMON";
        private String text;
    }
}
```

新增配置接入点（与既有 18 个配置类一致）：

1. `GameConfigLoader`：新增常量 + `loadVictoryInteractionConfig()`。
2. `GameConfigRegistry`：新增字段、`init()` 加载、`getVictoryInteractionConfig()`、索引（按 `winnerType + style`）。
3. `GameConfigValidator`：校验 `winnerType / style / contexts / weight` 枚举与唯一 id。

## 83.3 BattleDefeatContext（轻量）

战败时由 `BattleService.settleBattle` 在既有战败分支处，从 `BattleContext` 聚合生成，只保留以下字段；**优先复用已有数据，不改造战斗引擎**：

- `winnerId`：Boss id / 训练师 id / null（野外宠物无固定 id）。
- `winnerType`：`TRAINER / WILD_PET / BOSS`（由 `battleType` 映射：`BOSS → BOSS`、`WILD → WILD_PET`、`TEST → TRAINER`）。
- `winnerHpPercent`：获胜方存活单位平均 HP 百分比。
- `turnCount`：`ctx.getCurrentRound()`。
- `challengeCount`（可选）：固定 Boss 的挑战次数（成本低才有）。
- `playerSwitchCount` / `playerHealCount` / `repeatedSkillCount`：由 `ctx.getEvents()` 简单统计 `PET_SWITCHED / ITEM_USED(治疗类) / SKILL_CAST` 事件得出。
- `playerAlmostWon` / `playerWasCrushed` / `playerWasComebackDefeated`：由事件序列推导（敌方最后残血 / 敌方几乎满血 / 敌方先倒后被反杀）。

若某字段现有系统不易获得，则**不为其改造战斗引擎**，直接降级（该项不参与标签判定）。

## 83.4 战况标签判定（首版 8 个）

由 `BattleDefeatContext` 计算，规则配置化、阈值可在 `system.yml` 微调：

```text
NORMAL_LOSS       默认
CLOSE_LOSS        敌方最终存活单位 HP 极低（如 < 15%）
CRUSHED           敌方损失极少（如最终 HP 比 > 85%）或玩家方几乎全灭且未造成有效伤害
COMEBACK_LOSS     玩家曾占据明显优势（敌方先倒 1 只且领先数回合）后被反杀
REPEATED_DEFEAT   连续败给同一固定敌人 ≥ 2 次（仅固定敌人）
EXCESSIVE_HEAL    玩家治疗事件次数超阈值
EXCESSIVE_SWITCH  玩家主动换宠次数超阈值
REPEATED_SKILL    玩家同一技能使用次数超阈值
```

## 83.5 选择算法

```text
候选池 = 所有 winnerType 匹配 且 style 匹配 且 contexts 命中/interaction.contexts 为空 的 interaction
若为空 → 回退到 winnerType 匹配 + contexts 命中的公共池
再为空 → 回退到默认旁白（纯文本）
排除最近 3～5 条 interactionId
按 rarity 过滤（COMMON 全量；EASTER_EGG 额外 1%～3% 概率入场）
按 weight 加权随机
```

防重复：以 `saveId` 为粒度，在内存维护最近 3～5 条 interactionId 的环形队列（重启即清空，可接受；如需持久化可复用 `player_statistic`，首版不做）。

## 83.6 获胜方识别与角色名

- `BOSS`：`ctx.getBossId()` → `registry.getBoss(bossId).getName()`。
- `TRAINER`：当前第一阶段**没有训练师对战系统**（NPC 只对话不战斗），故 `TRAINER` 类型首版主要承载「测试战斗/TEST 固定敌人」与预留接口；配置层完整支持，未来接入真实训练师对战时无需改结构。
- `WILD_PET`：野外宠物无固定实例 id，取敌方存活单位名（species 显示名）作为旁白主语。

## 83.7 接入点（后端）

在 `BattleService.settleBattle` 的战败分支（当前 `handleDefeat` 处）新增一次调用：

```java
if (!playerWon && !ctx.isFled()) {
    // 原有战败流程（零惩罚）
    settlement.setDefeat(mapExplorationService.handleDefeat(player));
    // 新增：生成轻量战况上下文并选择胜利互动（REQUIRES_NEW，失败不阻断结算）
    settlement.setVictoryInteraction(
        victoryInteractionService.select(ctx, player.getSaveId()));
}
```

- `settlement.victoryInteraction` 为新增可选字段（null 表示无专属内容，前端隐藏互动区）。
- 顶层 `try/catch`，任何异常只记日志、返回 null，不阻断主结算。
- 缓存连接点：`player_statistic` 新增统计键 `BOSS_CHALLENGE_<bossId> / BOSS_CONSECUTIVE_DEFEAT_<bossId>` 或极小表，用于 `challengeCount / consecutiveDefeatCount`（固定敌人专用，普通野怪不写）。

## 83.8 前端播放（复用现有能力）

- 复用 `BattleView.vue` 战败面板（当前展示 `settlement.defeat.message`），在互动存在时优先展示互动区。
- 复用 `DialogueBox.vue` / 战斗对话框的文本展示样式；动作/叫声/表情按 `presentationType` 渲染，无对应资源时降级为纯文本/旁白。
- `battle.ts` store 增加 `settlement.victoryInteraction` 透传与类型定义。
- 不新建复杂动画框架；动作映射为简单 CSS/已有精灵待机切换即可。

## 83.9 存档边界

- 普通随机野怪：**不保存任何长期交互历史**。
- 固定 Boss / 精英 / 霸主：仅记录 `challengeCount / consecutiveDefeatCount`（复用 `player_statistic` 键或极小表），不新增复杂关系数据。
- 若需大幅改存档结构，推迟到后续版本。

## 83.10 降级策略

系统在资源不足时仍可工作：

- 一级：专属动作 + 叫声 + 文本。
- 二级：已有动作 + 文本。
- 三级：纯文本 / 旁白。

## 83.11 测试要点

- 提供专属配置时命中专属；无专属时回退公共池；无匹配时回退默认旁白。
- 同一互动短期不重复（防重复队列生效）。
- 各战况标签（CLOSE_LOSS / CRUSHED / COMEBACK_LOSS / REPEATED_SKILL 等）能正确触发对应互动。
- 战败结算不受互动异常影响（异常返回 null，不改 `settlement` 主流程）。
- 普通野怪不产生持久化写入；固定 Boss 挑战次数正确累计。
- 配置校验：非法 `winnerType / style / contexts / weight` 启动报错。

# 84. 动态难度、野外缩放、Boss 快照与有效等级技术方案

## 84.1 结构与边界

新增 `player.game_difficulty`（默认 `NORMAL`）和 Boss 遭遇快照表；其余内容配置仍放 YAML。全局难度配置归入 `SystemRuleConfig.GameDifficultyConfig`，地图数值边界归入 `MapsConfig.RegionConfig`，Boss 可选支援种族归入 `BossesConfig.BossConfig`。不新增服务、缓存、消息队列或第二套战斗引擎。

`BattleService` 继续是所有野外、Boss、自动挑战的唯一创建入口。`WildEncounterService` 接收当前区域、活动队伍和全局难度生成临时野外单位；`BossEncounterSnapshotService` 在开战前读取或创建持久快照；`BattleLevelResolver` 仅将玩家实体投影为战斗临时六维。BattleEngine 只读取 `BattleUnit`，不读取持久化宠物。

## 84.2 持久化与事务

Flyway 迁移新增 `player.game_difficulty` 与 `player_boss_encounter_snapshot`。快照唯一键为 `(save_id, boss_id, boss_difficulty)`，JSON 文本保存完整已生成队伍，以保证服务重启、外部配置变更后仍可复用同一遭遇。首次创建使用事务和唯一约束防并发重复；显式重置先验证当前全局难度与快照难度不同，再原子替换。战斗过程仍零数据库写入，结算仍由既有事务负责。

## 84.3 有效等级数据约定

`BattleUnit.level` 保持真实等级兼容奖励与捕获；新增 `actualLevel` 与 `effectiveLevel` 用于展示。战斗六维始终是有效属性值。玩家有效 HP 以原 HP 比例映射到有效最大 HP；结算回写 HP 时将比例映射回真实最大 HP，避免等级压制战斗污染存档。

`PetGrowthService.computePanelStatsAtLevel` 是唯一成长公式。投影自由点前复制轻量 `PlayerPetEntity` 数据，不写数据库；速度成本等规则仍复用 `PetGrowthService`。

## 84.4 接口

- `GET /api/game/difficulty`：当前全局难度与档位说明；
- `PUT /api/game/difficulty`：校验并保存全局难度；
- `GET /api/bosses/{bossId}/snapshot?difficulty=...`：查询快照摘要与当前难度是否不一致；
- `POST /api/bosses/{bossId}/snapshot/reset`：仅在全局难度不一致时确认重置；
- 既有野外与 Boss 开战接口不改变意图参数，服务端自行读取设置、地图和快照。

接口响应仍使用统一 `{ success, data, message, code }`。前端只展示实际/有效等级和快照摘要，绝不提交敌方生成结果或属性计算结果。

## 84.5 验证

配置校验覆盖四档难度、地图边界、Boss 可选种族/角色引用与倍率。单元测试覆盖缩放夹取、快照锁定/跨难度重置限制、有效等级和自由点投影；回归测试覆盖现有 BattleEngine 伤害、治疗、速度、状态、捕获、奖励与结算。
