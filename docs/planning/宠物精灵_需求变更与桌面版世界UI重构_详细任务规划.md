# 宠物精灵需求变更与桌面版世界/UI 重构详细任务规划

> 文档性质：基于 2026-08-19 当前仓库实际实现形成的后续开发任务基线。  
> 本文只做现状分析、需求差异识别和开发任务规划，不代表相关功能已经实现。  
> 改造原则：保留已经稳定的玩法与服务，增量建立“世界常驻 + 游戏内窗口”交互，不引入新基础设施，不推倒重写。
> 执行状态：阶段 0 已于 2026-08-19 完成；正式裁决与证据见 `docs/development/PHASE0_BASELINE.md`。

## 1. 规划背景

项目第一阶段的宠物、队伍、技能、背包、捕捉、Boss、自动战斗、任务、成就、存档与开发者工具等业务能力已经形成，前后端也具备完整构建和较高覆盖度的后端测试。但当前产品形态仍主要是“多个 Web 页面通过路由相互跳转”，地图层则是由单个区域对应单张 Tiled 地图的探索页。

本次变更要求桌面版逐步转为以世界探索为中心的游戏形态：地图世界成为常驻根容器，宠物、队伍、背包、任务、图鉴、商店、战斗等能力在世界上层以窗口、抽屉、浮层或覆盖层联动；世界结构从“区域卡片 + 单图”演进为“世界—区域—地图”三层；战斗、传送、任务和世界变化均能恢复到正确的探索上下文。

此次改造不是重做已有玩法。后端 `BattleEngine`、宠物培养、技能、物品、捕捉、Boss、自动战斗等稳定业务逻辑应继续作为唯一规则来源；主要工作集中在世界领域模型、探索会话持久化、前端容器生命周期、跨页面上下文和桌面端交互表现。

### 1.1 本规划回答的问题

1. 项目现在是什么状态：以当前源代码、配置、数据库迁移、Tiled 地图、资源和测试结果为依据说明。
2. 为满足新需求具体要改什么：用“当前实现 → 新需求 → 修改”记录重要差异，并区分已完成、可复用、需完善、需重构、未实现和需废弃能力。
3. 应按什么顺序开发：先解决文档与架构基线，再完成一条区域纵切，验证世界—战斗—页面联动闭环后扩展全世界，最后处理表现、响应式边界和总验收。

### 1.2 范围边界

- 本轮目标是桌面版世界与 UI 重构，以及支撑该目标所需的数据、接口、状态和测试调整。
- 不新增微服务、WebSocket、Redis、消息队列、复杂事件总线、登录/多用户等基础设施。
- 不改变已有宠物数量、属性体系、战斗公式、捕捉公式、队伍规则等玩法，除非新的权威需求明确覆盖旧规则并完成文档裁决。
- 新需求文档 R-001 与用户最新确认均明确本轮只做桌面端。手机、平板、触控专用布局及其专项回归全部不在本规划范围内，也不作为任何阶段或最终验收项。
- “20～35 张有意义地图”“每区域 4～7 张地图”为设计目标而非机械凑数。没有明确体验职责的地图不得为满足数量而创建。

## 3. 当前项目实际实现概览

### 3.1 技术与质量基线

| 领域 | 实际状态 | 结论 |
|---|---|---|
| 前端 | Vue 3 + TypeScript + Vite + Pinia + Vue Router Hash 模式 + Phaser；18 个顶层路由 | 技术栈符合既定方案，但页面组织仍偏传统 Web |
| 后端 | Java 21 + Spring Boot 3.5.x + MyBatis-Plus；单体模块化 | 可继续承载新世界接口，无需拆分架构 |
| 数据库 | MySQL + Flyway；内容配置在 YAML、玩家存档在数据库 | 分层原则正确，但缺少位置、知识和世界状态存档 |
| 前端验证 | `vue-tsc` 与 Vite 正式构建通过 | 当前代码可构建；`ExploreView` 产物约 1.71 MB（gzip 约 391 KB），已有大块告警 |
| 后端验证 | Maven 测试 512 项，0 失败、0 错误、0 跳过 | 核心业务回归基线稳定；历史 507/阶段 0 前 511 均已过期 |
| 前端自动化 | 未配置组件测试/浏览器 E2E；现有 PowerShell “E2E”主要验证 API | 无法自动证明浮层、焦点、返回上下文和地图生命周期 |

### 3.2 前端页面、路由和世界容器

- `frontend/src/router/index.ts` 注册首页、新游戏、探索、世界地图、战斗、宠物、队伍、仓库、图鉴、Boss、背包、商店、任务、成就、统计、设置、存档备份、开发者工具等顶层路由。
- `frontend/src/App.vue` 通过 `MainLayout` 承载 `RouterView`。`MainLayout.vue` 顶栏仍以 `RouterLink` 作为主导航；从探索页跳到功能页会卸载 `ExploreView`，进而销毁 Phaser 实例。
- `stores/overlay.ts`、`OverlayLayer.vue`、`OverlayShell.vue` 已能把战斗、队伍、宠物、背包、图鉴、任务、世界地图、NPC、商店等页面嵌入浮层，是本次改造最重要的可复用基础。
- 当前 Overlay 分为 0～3 级暂停，但与新 Context Stack 尚不等价：NPC 对话只阻止玩家移动，野怪仍可更新；部分确认框和奖励弹窗仍由页面本地布尔值管理。
- `MainLayout.vue` 的全局按键监听未判断按键类型，当前任意按键都可能触发 `handleEscape()` 并关闭顶层 Overlay；`OverlayShell.vue` 也缺少初始焦点、焦点陷阱、关闭后焦点恢复和完整 ARIA 语义。
- `useKeyboardShortcuts.ts` 已支持 T/B(I)/M/Q/P/G/S，但与新需求冲突：Q 目前打开任务而非快速队伍，J 未使用，S 与 WASD 向下移动冲突。

### 3.3 世界地图与探索

- `ExploreView.vue` 是 Phaser 探索宿主页，挂载时创建、卸载时销毁游戏。只有在该页内部打开战斗浮层时地图生命周期才能暂时保留。
- `MapScene.ts` 使用固定 800×608 视口，读取 25×19、32 像素瓦片的 Tiled 地图；当前没有相机跟随、死区、方向前视或保存后的相机恢复。
- 现有 6 张地图：初始村庄、草甸、森林、水域、雷地区、遗迹；配置模型 `MapsConfig.RegionConfig` 实际把“区域”和“地图”合并为同一对象。
- 已实现 Tiled 出生点、出口、营地、采集点、宝箱、伏击、Boss、NPC 和可视野怪。野怪具备游荡、胆小、主动追击、稀有驻留等行为，可直接复用。
- 普通出口目前是接触后弹确认框，确认后调用进入接口并重启 `BootScene`；不符合连续世界的普通门径切换，也无法保留精确位置、朝向和相机。
- 前端 `mapStore` 只有当前地图、世界地图、客户端位置、附近对象等运行态；后端 `player` 只保存 `current_map_id`，没有当前区域、地图、坐标、朝向、相机、返回上下文和已知世界信息。
- `ContextInteractionPanel` 已存在，但 `ExploreView` 没有订阅 `object:proximity`，实际无法稳定获得附近对象。`MapScene` 的附近对象变化只比较 `type`，同类型对象切换也可能漏发。
- 地图上的野怪和交互物常驻显示文字标签，缺少 FAR/NEAR/ACTIVE 信息密度规则；主动怪只有追击，没有预警、安全区或战后保护。

### 3.4 实际地图连通性与内容接入问题

| 问题 | 实际证据 | 影响 |
|---|---|---|
| 配置与 Tiled 出口不一致 | 森林配置声明通向草甸、水域、雷地区；Tiled 森林仅有返回草甸的出口 | 水域、雷地区无法通过实际步行入口到达 |
| 遗迹缺少返回出口 | 水域/雷地区可指向遗迹，但遗迹 Tiled 和 YAML 都没有出口 | 玩家进入后无法依靠世界内路径返回 |
| Boss ID 不一致 | Tiled 使用 `BOSS_MEADOW`、`BOSS_FOREST`，Boss 配置使用 `BOSS_MEADOW_GUARDIAN`、`BOSS_FOREST_KING` | Boss 页会走兜底逻辑，可能打开错误 Boss |
| NPC 未放入地图 | NPC 配置含迷路旅人、阴影精灵、森林商人，Tiled 中无对应对象 | 对话、商店和部分任务无法从真实地图触发 |
| 世界变化未作用于场景 | 后端 `MapEnterView` 返回 `activatedMapChanges`，前端类型和 `GameBridge` 未携带，`MapScene` 未消费 | 捷径、桥梁、NPC、额外营地等永久变化只有文本结果，没有实际地图效果 |
| 缺少跨源校验 | 当前校验能验证 YAML 内部引用，但不解析 Tiled 对象和网关 | 不可达路径和 ID 漂移无法在构建/测试时发现 |

### 3.5 战斗、捕捉、Boss 与自动战斗

- 后端 `BattleEngine` 是手动/自动/普通/精英/Boss 的统一规则入口，伤害、捕捉、奖励和结算均由后端计算；该边界与新需求一致，应保持不变。
- `BattleOverlay.vue` 已能在探索页上层展示战斗、操作、日志、捕捉和结算卡片；`BattleView.vue` 仍保留另一套大型独立页面实现，二者存在长期漂移风险。
- 战斗胜利时前端会标记野怪为已击败，但没有向当前 Phaser 场景发送移除指令；逃跑时没有解除野怪 `engaged` 状态，也没有回退位置或安全宽限，可能留下不可再次交互的实体。
- 失败结算后端会返回复活点并恢复队伍，但 `ExploreView` 未把复活点应用到地图场景，实际仍可能停留在原位置。
- Boss 战可以从 Overlay 打开，已有多难度、首次/重复奖励、情报与自动挑战规则；胜利后的永久世界变化尚未映射到场景行为。

### 3.6 宠物、队伍、技能、物品、任务等功能

| 系统 | 当前实现 | 新需求下的判断 |
|---|---|---|
| 宠物/图鉴 | 27 宠，详情、培养、技能配置、图鉴状态和资源引用已实现 | 业务可复用；页面需转为常驻世界上的可嵌入窗口并保留子上下文 |
| 队伍 | 6 宠携带、3 宠上场、5 预设及快速队伍能力已实现 | 规则可复用；快捷键与快速窗需重排 |
| 技能 | 85 主动 + 51 被动，固有/技能书来源和槽位规则已实现 | 无需重做；仅适配窗口和战斗展示 |
| 背包/道具 | 45 道具，使用、出售/购买和目标选择等已实现 | Service 可复用；战斗中允许范围必须先裁决 |
| 捕捉 | 公式、球档位、结算及收纳逻辑已实现 | 规则可复用；重点改造遭遇返回和实体消失 |
| Boss | 8 个配置，难度、掉落、自动条件已实现 | 业务可复用；需修正地图入口 ID、返回点和世界变化 |
| 任务/NPC/商店 | 25 任务、NPC 对话和商店 Overlay 已存在 | 任务位置绑定仍依赖 region/raw ID；NPC 商店开启存在硬编码 |
| 成就/统计/存档/开发者工具 | 已实现并有后端测试 | 以二级窗口或设置入口复用，不提升为世界主导航 |

多数功能 View 把标签页、筛选、当前选择、滚动位置存为组件本地状态，并在 `onMounted` 重新加载。直接关闭/重新打开会丢失用户刚才的浏览上下文，尚不满足“关闭后自然回到原探索状态、嵌套打开后按层返回”的要求。

### 3.7 后端、数据库与内容配置

- `MapExplorationService` 和 `/api/maps/**` 已提供世界摘要、进入区域、营地、传送、采集、宝箱、遭遇和随机事件能力，可作为新世界服务的增量改造起点。
- 现有存储包括 `player.current_map_id`、`player_region_unlock`、`player_camp_activation`、`player_chest_loot`、`player_map_session`、`player_gather_used` 以及任务进度/地图变化相关表；可以保存“进过哪张图、用过哪些对象”，但不具备精确坐标、朝向、相机、已知连接和 WorldTruth / PlayerKnowledge / WorldState 分层。
- `WorldMap` 接口返回扁平区域卡片，Boss 状态仍写死为 `NOT_OPEN`；尚无地图节点、连接、门径、地标、锚点、区域内地图层级和路径查询。
- 任务和地图变化配置按 `regionId`、对象原始 ID 绑定，缺少“区域 + 地图 + 语义锚点/位置”的稳定引用。
- 当前内容规模为 6 个区域配置（据点 + 5 区域）、6 张 Tiled 地图、6 遭遇组、6 随机事件、8 Boss、25 任务、33 成就；“配置数量存在”不等于“可从世界中到达并正确交互”。

### 3.8 美术与资源

- 当前约有 292 张 PNG 和 6 张 Tiled JSON，目录已覆盖宠物、Boss、物品、NPC、事件、特效、背景、UI、地图和角色精灵，资源访问辅助能力可继续复用。
- 地图资源只有 6 张 JSON + 5 张 tileset PNG，尚不够支撑三层地图、区域地标、网关状态、多个功能地图和动态环境状态。
- 未发现音频资源；新需求中的脚步、碰撞、进入战斗、按钮、胜负等音效需新增资源与轻量播放管理。
- 现有资源尺寸和用途已较明确，但新增世界/区域/小地图资源必须建立切图、锚点、分层、命名和压缩检查，避免继续通过页面内硬编码引用。

## 4. 需求与当前实现差异

### 4.1 分类结论

#### 已经完整实现，无需调整业务规则

- 后端统一 `BattleEngine` 与“前端只提交行动意图”的计算边界。
- 宠物基础数据、培养、队伍、主动/被动技能规则。
- 背包库存、商店账务、捕捉公式与奖励结算。
- Boss 多难度、自动战斗解锁条件、任务/成就/统计/存档备份等核心 Service。
- YAML 内容配置与玩家存档分离、Flyway 管理表结构、统一 REST 响应等技术边界。

以上能力仍需做 UI 容器或上下文适配，但不应重新实现业务逻辑。

#### 已经部分实现，需要完善

- Overlay 栈、统一遮罩壳、快速队伍、地图 HUD、上下文交互面板。
- Phaser 可视野怪、出口、NPC、Boss、宝箱、采集点、营地和随机事件。
- 世界地图区域列表、任务/图鉴到地图的简单联动。
- 战斗 Overlay 和战斗后结算卡片。
- 桌面 CSS 基础和美术资源路径管理；仓库虽存在小屏样式，但本次不分析或改造其适配效果。

#### 已实现，但与新需求冲突，需要重构

- 以顶层路由和全局导航栏作为主交互方式。
- “一个 RegionConfig 等于一张地图”的世界模型。
- 世界地图 Overlay 内部仍 `router.push('/explore')` 的跳转方式。
- 接触普通出口后弹确认并重启场景的切图方式。
- 战斗页与战斗 Overlay 两套大体量 UI 实现。

## 5. 总体改造思路

### 5.1 核心路线

采用“保持核心规则，替换产品壳；先做一条纵切，再扩展内容”的策略：

1. 先裁决冲突，固定当前回归基线。
2. 让探索世界成为常驻根，统一浮层、输入和返回上下文。
3. 在后端/配置中建立最小 WorldGraph 和存档模型，不引入通用图框架。
4. 选择“据点 → 森林入口 → 林间路径 → 营地/深处 → Boss 场”完成一条可玩纵切。
5. 在纵切上打通地图知识、导航、遭遇、战斗、页面窗口、任务和永久世界变化。
6. 纵切验收后再按相同契约扩展草甸、水域、雷地区、遗迹等内容。
7. 最后补齐动态世界、音频、桌面表现、性能、可访问性和总回归。

### 5.2 状态分层

| 层 | 职责 | 典型内容 | 禁止事项 |
|---|---|---|---|
| WorldTruth | 静态世界事实 | 区域、地图、连接、网关、地标、锚点、地图职责 | 不保存玩家进度，不把规则复制进 Phaser |
| PlayerKnowledge | 玩家已知信息 | 已发现区域/地图/连接/地标/安全点、地图知识状态 | 不泄露未知隐藏路线和未发现 Boss |
| WorldState | 存档中的动态世界 | 当前区域/地图/坐标/朝向、安全点、捷径、任务变化、Boss 变化、环境状态 | 不复制宠物/技能等内容配置 |
| Session/Context | 临时交互上下文 | Overlay 栈、ReturnContext、追踪任务、窗口标签/选择、遭遇锁 | 不作为业务结算事实源，不用刷新替代必要持久化 |

### 5.3 增量兼容原则

- 先让现有 Region ID 通过兼容映射落到新 Map ID，随后逐图拆分；迁移期接口可同时返回旧字段和新字段，待所有调用方迁移后再删除旧字段。
- 现有功能 View 优先改造成可嵌入组件，不为 Overlay 再复制一套业务页面。
- Phaser 继续只处理场景表现和输入；图谱、知识、任务条件、战斗结算由 Vue/后端负责。
- 不引入新的全局状态框架；继续使用 Pinia，并只新增确有跨页面生命周期需求的 Store 状态。
- 每个阶段保留可运行版本；旧路由在兼容期仍可访问，但不得再作为新桌面玩法的主路径。

## 12. 阶段 5：可视遭遇、战斗覆盖层与返回闭环

### 12.1 阶段目标

在常驻世界上完整打通“发现威胁 → 警示/追击 → 接触 → 战斗覆盖层 → 胜利/捕捉/逃跑/失败/Boss 结算 → 正确地点恢复”的核心循环。

### 12.2 当前情况

### 12.3 详细任务

1. 定义遭遇状态：IDLE/WANDER、ALERT、CHASE、ENGAGED、COOLDOWN/REMOVED；明确各状态的移动、提示、接触和保存语义。
2. 为主动怪加入可识别的警示阶段、追击半径/时间上限、脱战返回和地图边界；切图后不得跨地图追击。
3. 把营地、传送到达点、普通 Gateway 到达点和剧情对话区域标为安全/保护区，主动怪不得在保护期间立即触发。
4. 建立 Battle ReturnContext：来源 mapId、玩家位置/朝向、遭遇实体 ID、建议安全回退点、场景版本、战斗类型和 Boss 场地信息。
5. 战斗触发时先由后端验证遭遇/目标，再保存关键位置，设置 ENCOUNTER 锁并打开唯一 Battle Context；失败启动时解除所有输入锁并恢复实体状态。
6. 以 `BattleOverlay.vue` 作为玩家主流程唯一战斗 UI，抽取和复用 `BattleView.vue` 中仍有价值的展示组件；迁移完成后将 `/battle` 限制为开发/兼容入口或删除重复页面实现。
7. 消除 `battleOpen` 与 Overlay Store 双重事实源；战斗是否显示、能否关闭和结算状态由同一 Battle Context 决定。
8. 胜利：应用后端结算、移除/标记场景实体、在原位置恢复、给予短暂保护，并保证重复结算幂等。
9. 捕捉成功：与胜利相同地移除实体，但按现有规则不结算击败掉落；队伍/仓库结果由后端事实更新。
10. 逃跑：后端确认结果后清除 `engaged` 和遭遇锁，将玩家放到 ReturnContext 的安全回退位置，实体进入短冷却，避免同一帧再次触发。
11. 失败：使用服务端返回的最近有效已激活安全点，完成跨图/同图传送、队伍恢复、镜头和输入重置；目标无效时落到区域默认安全点。
12. Boss：战斗 Overlay 关闭后回到原 Boss 场地；胜利标记 Boss 状态、移除/改变入口表现并为阶段 7 的世界变化提供统一事件。
13. 自动战斗继续调用同一 BattleEngine 和同一结算/返回流程；“谁决定行动”之外不得分叉奖励、捕捉或世界状态逻辑。
14. 处理刷新/重启边界：战斗临时状态仍按既定规则丢弃；客户端重新进入时根据服务端当前战斗/位置规则回到安全一致状态，不展示幽灵 Overlay。
15. 针对 R-043 的裁决统一战斗背包：只展示服务端声明可用的现有库存，前端不自行推导允许范围；若最终裁决禁止手动道具则移除玩家入口但保留业务兼容测试。

## 16. 阶段 9：轻量动态世界与音频反馈

### 16.1 阶段目标

在稳定的世界状态模型上增加低成本但可感知的昼夜、有限天气/环境事件和核心音效，使世界有变化但不演变成复杂实时模拟。

### 16.2 当前情况

- 当前没有音频资源和统一音频管理。
- 地图画面为静态 Tiled/背景，没有游戏内时间、天气或低频事件状态。
- 后端已有随机事件能力，但它与视觉环境、世界时段和低频触发尚未统一。

### 16.3 详细任务

1. 根据阶段 0 裁决定义最小游戏内时间模型：离散时段、推进触发、保存字段和重启行为；不与现实时间绑定。
2. 定义有限环境状态表，例如晴/雨/雾等本轮确认集合；每个区域只启用适合的子集，不实现复杂天气预测和元素反应。
3. 将时间/天气/低频事件作为 WorldState 版本化保存，提供当前地图所需投影；客户端不能自行决定会影响玩法的状态。
4. 在 Phaser 中用轻量色调、粒子、覆盖层或环境物变化表达；优先复用原生 Phaser/CSS 能力，避免引入大型特效库。
5. 明确哪些动态状态只影响氛围，哪些影响可见性/遭遇/任务；所有玩法影响必须服务端判定并有测试。
6. 将现有随机事件接入区域/地图/时段条件；设置低频和冷却，避免切图/刷新反复触发。
7. 建立最小音频管理：主音量/音效音量、静音、资源预载/懒加载、重复播放限制和浏览器自动播放限制处理。
8. 首批接入脚步/移动反馈、交互、碰撞/警示、进入战斗、按钮、胜利、失败和捕捉结果等高价值音效；环境音/音乐按资源情况后续增量。
9. 设置页面增加音量和静音项并持久化；失焦/隐藏时按策略暂停或降低环境音，恢复时不叠加播放。
10. 为低性能设备提供关闭天气粒子/降低动态效果的设置，但不改变世界事实和玩法结果。

### 16.4 涉及模块

- WorldState/随机事件相关后端配置、Service、DTO 和数据库迁移。
- `MapScene.ts`、探索 Store/HUD、设置 Store/View。
- 前端现有资源工具和新音频资源目录。
- 区域/地图环境配置、美术覆盖层和粒子资源。

### 16.5 实现要求

- 不使用现实时间刷新，不实现季节、复杂预测、全局实时同步或后台定时任务基础设施。
- 动态世界必须是有限状态，配置错误有默认状态；视觉层不反向修改业务状态。
- 音频在用户首次交互前不得强制播放；资源失败不能阻断地图或战斗。
- 同一事件的画面、音效和业务结果需要共用事件 ID/状态，不创建三套互不一致的随机逻辑。

### 16.6 验收标准

- 游戏内时段按定义的游戏行为推进，刷新/重启后保持；修改系统时钟不会改变状态。
- 至少两种本轮确认的环境状态在适用地图上有可辨别表现，不适用区域不会随机出现。
- 同一低频事件在冷却期内切图/刷新不会重复结算；其业务结果仍由后端决定。
- 关闭天气效果只移除视觉开销，不改变服务端遭遇/任务判定。
- 首次打开页面不会触发浏览器自动播放错误；用户交互后关键按钮、警示、战斗进入、胜负和捕捉有对应反馈。
- 静音和音量设置刷新后保留；页面失焦再恢复不会出现多个音频叠加。
- 音频或特效资源加载失败时，地图、战斗和结算仍可完成，并显示非阻断错误记录。

### 16.7 阶段完成定义

动态环境和音频在不改变核心规则、不引入实时基础设施的前提下稳定运行，设置可控，失败可降级，相关后端/前端测试通过。

- 性能优化以浏览器分析证据为准；不为包体数字引入复杂微前端或新状态框架。
- 可访问性基础不能因追求短代码被省略；动效必须可减弱，关键状态需文本/图形双重表达。
- 不为手机、平板或触控交互增加兼容分支；桌面布局验收不得被小屏样式牵制。

### 17.6 验收标准

- 在五种目标桌面分辨率下，地图是最大视觉区域；HUD 不覆盖玩家周围主要交互区，所有窗口可完整操作且无水平页面滚动。
- 地图中心不存在无上下文的常驻对象名/长文本；靠近、聚焦或任务要求时提示正确出现和消失。
- Overlay 的标题、关闭/返回、滚动、确认、危险按钮和加载/错误状态在全部核心功能中一致。
- `prefers-reduced-motion` 开启后地图/战斗/窗口动效显著降低，但操作时序和结果不变。
- 连续打开/关闭同一功能窗口 50 次、进行 20 次切图后，事件只触发一次，不出现重复音效、重复 API 请求或明显持续增长的场景/监听器数量。
- 正常初始探索不下载尚未进入的全部区域 Tiled/大背景；进入目标区域时按设计预载且失败可回退。
- 探索构建块不再包含可由 Overlay 懒加载的全部功能和重复战斗实现；若仍超过阈值，构建报告中有可解释的 Phaser 基础占比和后续记录。
- 键盘焦点在所有阻塞窗口可见，读屏名称存在，关键警告不只依赖颜色。

### 17.7 阶段完成定义

桌面分辨率、HUD/窗口一致性、资源加载、内存/监听器和可访问性用例全部通过；核心状态模块无需再因视觉调整被修改。

- 阶段 1、2、5 为高风险重构，应拆成小批次合并：兼容层先落地 → 新路径接入 → 验收 → 再删除旧路径。
- 所有数据库变更均新增 Flyway，并在合并前用旧存档样本验证；不允许先改 Entity 后补迁移。
- 所有世界内容批量变更都必须先让校验器在当前已知错误上“红”，修复后再“绿”，证明校验确实有效。

### 21.1 已由代码确认的高风险

| 风险 | 实际依据 | 可能后果 | 控制措施 |

| 路由改 Overlay 导致地图生命周期变化 | `ExploreView` 随路由卸载并销毁 Phaser | 位置、怪物、相机和局部交互重置 | 阶段 1 先常驻根；用实例 ID 和状态快照做 E2E |

| 战斗返回路径不完整 | 胜利不发场景移除、逃跑不解锁、失败不应用复活点 | 幽灵怪、重复遭遇、错误位置或软锁 | ReturnContext + 五类结算状态机 + 幂等测试 |
| 功能 View 本地上下文丢失 | 标签/筛选/选择大多只存在组件内 | 嵌套返回体验断裂、重复加载 | 只提升必要 UI snapshot 到 Context/Pinia |
| 战斗 UI 重复 | `BattleOverlay.vue` 与 `BattleView.vue` 均为大组件 | 修复一处另一处漂移、包体增大 | 选定 Overlay 为唯一玩家路径，逐步抽取/删除重复逻辑 |

| 旧存档迁移风险 | 新模型需要位置/知识/世界状态，当前表不具备 | 旧玩家进入非法位置或丢进度 | 版本化 Flyway、三类真实样本、默认锚点和回滚备份 |
| 探索包和资源继续膨胀 | 当前 Explore 块约 1.71 MB，已告警 | 首载、切图和内存恶化 | 功能懒加载、地图按区加载、去除重复战斗实现、构建报告 |
| 音频资源完全缺失 | 仓库未发现音频文件 | 阶段 9 资源与权限处理工作量不确定 | 先做最小高价值声音集，失败可降级，不阻断玩法 |

### 21.2 实施注意事项

- `MapScene` 中目前有多个对象和野怪行为分支。新增 Gateway/WorldChange 时应通过共同的数据映射入口处理，不在每张地图增加 `if (mapId === ...)`。
- `mapStore.markWildDefeated` 目前只改变数组。修复实体移除时必须检查所有调用方，避免只修普通胜利而遗漏捕捉/Boss/自动战斗。
- `WorldMapView` 既能作为旧路由又能嵌入 Overlay。迁移时避免在组件内部直接决定路由；导航动作由容器上下文注入或统一处理。
- NPC 商店硬编码必须由后端动作字段取代，但动作类型应保持有限枚举，不能演进为任意前端命令执行。
- 当前 `gameStore` 和部分组件使用 `any`。新世界 DTO 和 Context/ReturnContext 必须使用明确类型；不要求本轮顺带清理全仓库所有 `any`。
- 配置内容数量已经达到第一阶段上限。地图扩展的重点是组织和接入现有内容，不借机新增大量宠物、技能、道具、任务或 Boss。
- WorldGraph 校验失败应直接阻止开发/测试构建；生产运行时仍需给出清晰启动错误，不使用静默兜底掩盖坏配置。
- 开发者工具的传送/开图能力会绕过正常探索，E2E 必须同时包含“正常玩家路径”，不能只靠开发者操作证明可达。
- 常驻 Phaser 后要显式管理 listener/watch/loader 生命周期；“不卸载世界”不等于监听器永不清理。
- 桌面端分辨率验收应包含浏览器缩放 100% 的统一基线；系统 DPI 可另作抽查，但不为移动端或触控扩大范围。

## 22. 最终整体验收标准

以下所有项目都能明确判定通过/不通过。手机、平板和触控适配不在本轮验收范围内。

### 22.1 世界地图与探索流程

- 创建/加载存档后进入常驻世界根；主玩法不需要回首页或通过顶栏路由切换。
- World→Region→Map 层级由同一 WorldGraph 提供；当前地点、Connection、Gateway、Anchor 和地标引用一致。
- 据点及全部本轮区域可以通过合法世界路径到达和返回，不存在无说明孤岛或只能依靠开发者传送到达的主内容。
- 普通 Gateway 连续切图不弹确认、不切路由；危险/单向/关键剧情入口才按配置确认。
- 玩家位置、朝向、相机、已应用世界变化和探索知识按规则保存；刷新/重启后恢复到合法状态。
- 可视野怪具备警示、追击、脱战、安全区和跨图终止；不会在对话、战斗或保护期继续触发。

### 22.2 地图知识、导航与状态保持

- 世界图、区域图、小地图只展示 PlayerKnowledge 允许的信息；未发现隐藏路线不会出现在普通客户端响应中。
- 地图能区分未知/发现/探索、隐藏路线/捷径、安全点发现/激活/可用等状态。
- 同时只追踪一个任务/地标；软导航只指向已知可通行 Gateway，不提供自动探索或逐格自动路径。
- 打开/关闭地图窗口不销毁 Phaser，不改变当前地点；从任务/图鉴进入地图后按来源层级返回。
- 捷径、桥梁、NPC、营地、Boss 场等永久变化在当前场景即时生效，切图/刷新/重启后保持。

### 22.3 战斗触发、结算与退出

- 地图接触敌人后不发生页面路由跳转；Battle Overlay 显示在当前世界上层，战斗期间地图输入和 AI 冻结。
- 胜利后 Overlay 关闭，玩家回到原地图合理位置，目标实体消失，奖励只结算一次。
- 捕捉后实体消失，宠物归属和背包数量正确，且不错误结算击败掉落。
- 逃跑后清除遭遇锁，玩家到安全回退点，目标进入短冷却，不立即重复战斗。
- 失败后玩家到服务端选定的最近有效安全点，队伍恢复正确，原场景不残留战斗状态。
- Boss 战使用同一 BattleEngine；胜利/失败后回正确 Boss 场或安全点，永久世界变化和奖励事务一致。
- 手动、自动、普通、精英、Boss 不存在第二套计算或结算逻辑；战斗道具行为与阶段 0 裁决一致。

### 22.4 页面浮层与功能联动

- 宠物、队伍、背包、任务、图鉴、NPC、商店、Boss、仓库、成就、统计、设置等均可从世界内打开，不依赖顶层路由跳转。
- Overlay/Context 后进先出；Esc 只关闭允许关闭的栈顶，浏览器返回优先处理游戏上下文。
- 对话、确认、战斗等阻塞上下文的世界暂停级别正确；非阻塞提示不会阻止移动。
- 功能窗口关闭后回原探索状态；嵌套窗口返回时保留来源的标签、筛选、选择和滚动锚点。
- Q/B/J/M/E/WASD 等快捷键含义一致；输入框、组合键、失焦和窗口切换不会误触发或造成持续移动。
- 阻塞窗口具有初始焦点、焦点边界、关闭后焦点恢复、可见焦点样式和必要 ARIA 信息。

### 22.5 宠物、队伍、背包和原有系统回归

- 27 宠、队伍/预设、主动/被动技能、背包/商店、捕捉、Boss、自动战斗、任务、成就、统计、备份/恢复和开发者工具的既有规则全部通过回归。
- UI 容器改造不改变后端战斗公式、奖励、捕捉率、技能来源/槽位、队伍限制和库存账务。
- 写操作后只更新受影响数据；关闭 Overlay 不重置地图，也不重复提交业务操作。
- 旧功能路由在明确兼容期内结果与 Overlay 一致；退出兼容期后无玩家主流程引用。

### 22.6 状态管理、API 与数据一致性

- WorldTruth、PlayerKnowledge、WorldState、Session/Context 边界清晰；数据库不复制内容配置，Phaser 不承载业务规则。
- 前后端 DTO 对齐，`activatedMapChanges` 等已知缺失字段得到处理；非法位置、连接、知识和传送请求由后端拒绝。
- 地图切换、战斗结算、捕捉、任务、营地、捷径、Boss/世界变化和快速旅行均按自动保存矩阵落库。
- 网络重试和重复结算不会重复奖励、重复捕捉、重复世界变化或覆盖更新的位置。
- 新数据库可初始化，旧存档可迁移；宠物、背包、任务和已完成内容不丢失，非法旧位置安全回退。

### 22.7 桌面 UI/UX 与表现

- 在 1280×720、1366×768、1440×900、1920×1080 和常见超宽桌面窗口下，地图为主视觉区域，核心交互不被遮挡，无水平页面滚动。
- HUD 遵循四岛/信息分层，画面中心约 50%～60% 无常驻大面板；地图标签按距离和上下文出现。
- 世界、功能窗口、战斗和系统提示的层级、标题、关闭/返回、按钮、加载/错误状态一致。
- 减少动效设置有效；关键状态不只依赖颜色；资源/音频失败时核心流程可降级继续。
- 不以手机、平板或触控场景作为本轮设计、测试或完成条件。

### 22.8 性能、异常与发布

- 初始探索不加载所有区域大资源；Overlay 功能和非当前地图按需加载，切图失败能回原安全状态。
- 常驻世界反复开关窗口、切图和战斗后无重复监听、重复 API、重复音效或持续明显内存增长。
- WorldGraph/Tiled/资源/任务/Boss/NPC/地图变化校验全部通过，不存在静默兜底配置错误。
- 前端 typecheck/build、后端全部测试、组件测试、浏览器核心 E2E、正式 Jar 新库/旧库启动全部通过。
- API 超时、切图中断、战斗重试、资源/音频失败、刷新和后端重启不会导致永久遮罩、软锁、重复奖励或存档损坏。
- README、架构、规范、开发状态、玩家指南和部署文档与最终源码及实际测试数字一致。

## 24. 规划执行规则

1. 每个阶段开始前核对前置完成定义；未满足时先修复前置，不用后续阶段绕过。
2. 每个开发批次必须列出：当前实现证据、计划修改文件/模块、数据迁移、回归范围、自动/手工验收和回退方式。
3. 公共协议变更先写契约测试，再迁移一个纵切调用方；验证通过后才批量替换。
4. 每个阶段结束时执行前端 typecheck/build、后端相关/全量测试，并更新开发状态；阶段 3 起同时执行 WorldGraph/Tiled 校验。
5. 任何核心玩法回归失败都应修复后再进入下一阶段，不能以“UI 重构中”作为暂时忽略理由。
6. 发现新需求与权威规则冲突时继续执行“记录问题 → 提供影响/建议 → 获得裁决 → 同步文档”，不由开发者静默选择。
7. 规划中出现的新增模型/表/组件名称为职责描述；实施时应遵循现有目录和命名规范，不为显得完整创建无调用方的空抽象。
8. 每阶段都保持项目可运行；旧路径的删除安排在新路径通过验收之后，并在同批次完成调用方搜索和文档更新。

---

本规划的核心交付顺序是：先使世界持续存在，再建立可信的世界图谱和存档；用森林纵切证明地图、战斗、窗口、任务和世界变化可以形成闭环；最后按同一契约扩展全世界并完成桌面体验与发布验收。已有稳定玩法继续复用，重构集中在当前确实不满足新需求的产品壳、世界模型和上下文衔接上。
